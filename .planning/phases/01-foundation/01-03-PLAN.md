Wire the Supabase/DB env vars to required-in-prod in `src/lib/env.ts` (Plan 01 stubbed them optional). Run `drizzle-kit push` after the schema is finalized so the live DB matches.

Purpose: RLS is the backstop that physically cannot leak a founder's data; the tRPC tenant context is the ergonomic layer; the schema-scan + two-user tests keep it green for ten more phases.
Output: a migrated Supabase DB, the tenancy/billing/jobs/legal schema, the RLS policies + the `NON_TENANT_TABLES` constant, the tRPC tenant context + the tRPC client/provider component, the env-var tightening, and the three tests. No Stripe/auth wiring yet (Plan 07), no Inngest functions (Plan 04) — this plan creates the `jobs` table but not the functions that write to it.

**This plan is `autonomous: false`** — it requires (a) a human to provision the Supabase Pro project and inject its connection strings / publishable+secret keys into Vercel env + `.env.local` (the executor cannot create the Supabase project), and (b) `drizzle-kit push` may prompt on a column rename (it is non-interactive for plain CREATEs; if it prompts, a human confirms). The executor does everything else.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| founder's browser → tRPC API | untrusted requests cross here; the session JWT + RLS decide what data is reachable |
| tRPC API → Postgres | queries run as the `authenticated` role with a `tenant_id` JWT claim; RLS is the physical backstop |
| service-role client → Postgres | a narrow RLS-bypassing escape hatch (webhooks, Inngest jobs, account deletion) — must never be exposed to a user session or `NEXT_PUBLIC_*` |
| migration SQL → live DB | a missing `ENABLE ROW LEVEL SECURITY` line ships an open table — the schema-scan CI test is the catch |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-12 | Information Disclosure | a new/existing tenant table ships without RLS or with a missing policy → cross-tenant read | mitigate | RLS default-deny convention in every CREATE TABLE migration; the `tests/rls/schema-scan.test.ts` CI gate fails the build on any table not in `NON_TENANT_TABLES` lacking RLS+policy |
| T-1-13 | Information Disclosure | a buggy query (forgotten `.where(accountId=...)`) leaks another tenant's rows | mitigate | RLS is the backstop — even a `SELECT *` returns only the JWT-claim tenant's rows; `tests/rls/two-user-isolation.test.ts` proves it across every table |
| T-1-14 | Elevation of Privilege | the Supabase secret/service-role key leaks into a client bundle or an SSR client holding a user cookie | mitigate | `getServiceClient()` is server-only with a header comment listing its only callers; the secret key is never in `NEXT_PUBLIC_*` (env.ts validates it as a server var); Code Reviewer + CI grep for `service` in client components |
| T-1-15 | Spoofing | a forged JWT `tenant_id` claim lets a user read another tenant | mitigate | the JWT is signed by Supabase (verified by Postgres' `auth.jwt()`); the Auth Hook that injects `tenant_id` runs server-side from the verified user→account mapping — a client cannot forge it |
| T-1-16 | Tampering | `drizzle-kit push` silently drops/renames a column losing tenant data | mitigate | plan is `autonomous: false` — a human reviews any interactive drizzle-kit prompt; migrations are reviewed; the live DB is on Supabase Pro with daily backups (D-01b) |
| T-1-17 | Information Disclosure | the `jobs` system rows (`account_id IS NULL`, e.g. the AI health-check) become readable by tenants | mitigate | no `authenticated`-role policy grants access to `account_id IS NULL` rows — default-deny covers them; only `getServiceClient()` reads them |
