**Full review comments:**

### [P1] Revalidate tRPC sessions with getUser() — `src/server/context.ts:85`
For `/api/trpc/*`, the proxy matcher runs but `classify()` returns `public`, so line 62 returns before the proxy's `getUser()` validation; the route then builds context via `createTRPCContext`, which uses `getSession()` here. A revoked Supabase session can therefore keep invoking protected tRPC procedures until the cached JWT expires, and `getRequestClient(session.access_token)` will also install claims from that un-revalidated token.

### [P1] Mark Stripe events processed only after side effects — `src/app/api/webhooks/stripe/route.ts:59`
The webhook commits the `processed_stripe_events` claim before `applySubscriptionState(event)` runs, so if any later database write throws, Stripe's retry sees the event as already processed and returns 200 without replaying the failed side effect. The 6-hour reconcile job only scans accounts that already have `stripe_customer_id`, so failures before that customer id is persisted, or partial failures that require immediate entitlement correction, are not reliably closed by retry.

### [P2] Preserve subscription events that arrive before checkout — `src/modules/billing/state.ts:181-182`
Stripe does not guarantee webhook ordering, and a `customer.subscription.created/updated` event delivered before `checkout.session.completed` stores `stripe_customer_id` will hit this `!account` path, return `null`, and still be treated as successfully processed by the caller. That leaves the subscription tier/period unmapped until the cron later discovers the customer, so add an account id to subscription metadata or otherwise avoid claiming these events as complete when the customer mapping is not present yet.

### [P1] Enforce one account per owner_user_id — `src/db/migrations/0000_sturdy_maestro.sql:25`
The auth hook and tRPC context both assume D-03's 1:1 `auth.users.id -> accounts.id` mapping, but `owner_user_id` is only a foreign key, not a unique key. Concurrent first-login callbacks can create multiple live accounts for one user, after which the hook's `LIMIT 1` and context's `findFirst` can choose different tenants, making JWT tenant claims and service-role tenant resolution nondeterministic.

### [P2] Redact recipient emails before logging — `src/lib/email/client.ts:91`
This logs the founder's email address as `to`, and the shared `SENSITIVE_FIELDS`/Sentry scrubber does not redact either `to` or `email`, so transactional sends, skips, and failures leak PII to logs/monitoring. Add email-recipient keys to the scrub list or log only a non-PII delivery identifier.

### Fix 1 — UNIQUE on `accounts.owner_user_id` (codex finding #4)

**New migration `src/db/migrations/0003_*.sql`:**
```sql
-- Phase 1 D-03 enforces 1:1 auth.users.id → accounts.id while deleted_at IS NULL.
-- Without this constraint, concurrent first-login callbacks (auth/callback/route.ts:62-71)

  ON public.accounts (owner_user_id)
```

### Fix 3 — Claim Stripe events AFTER side-effects (codex finding #2)

`src/app/api/webhooks/stripe/route.ts:55-108` — invert the ordering. Two patterns work:

**Pattern A (recommended) — two-phase claim:**
```ts
// 1) Run side-effects inside a transaction
// 2) On success, INSERT into processed_stripe_events as the LAST statement of the same tx
// 3) On commit failure or any throw, the claim row never appears → Stripe retries succeed
```
Requires moving `claimEvent` + `applySubscriptionState` into a single Drizzle `db.transaction(async (tx) => { ... })` block.

**Pattern B (simpler) — soft-claim with status:**
```ts
// processed_stripe_events.status: 'in_progress' | 'done' | 'failed'
// 1) INSERT (event_id, status='in_progress') ON CONFLICT DO NOTHING → return claimed bool
// 2) Run side-effects
// 3) UPDATE status='done' (or 'failed' with error)
// On retry: if claimed row has status='in_progress', allow re-execution; if 'done', dedupe.
```
Requires schema migration to add `status` column on `processed_stripe_events`.

Pattern A is atomic and simpler. Pattern B is more observable. Codex implied A by "claim-before-success" framing.

Then `src/inngest/functions/reconcile-stripe.ts:43` — relax the `isNotNull(stripeCustomerId)` filter to also catch accounts where `subscription_status === 'trialing' AND stripe_customer_id IS NULL` (signals a stuck checkout that the webhook never finished).
