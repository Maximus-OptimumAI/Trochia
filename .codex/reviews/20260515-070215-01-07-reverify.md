## NEW finding (Phase-1-followup work — NOT a regression of the merged stack)

### [P1] First-login tenant claim staleness — `src/app/auth/callback/route.ts:81-85`

**Defect:** OAuth callback flow currently runs:

1. `exchangeCodeForSession()` — Supabase mints the access token. JWT claims include `tenant_id` resolved by the `custom_access_token_hook`, which queries `accounts WHERE owner_user_id = auth.uid()`. On a brand-new sign-in this returns zero rows → `tenant_id` claim is NULL on the minted JWT.
2. The route then INSERTs the `accounts` row (PR-1's atomic upsert).
3. Redirect to `/onboarding` (or `/app`) WITHOUT a token refresh.

The cookie that gets set carries the JWT minted in step 1 — `tenant_id: null`. The hook is NOT re-run on the redirect because there's no new sign-in event; it's the same session. The token will only refresh when:
- It expires (≤1h TTL), OR
- The client explicitly calls `supabase.auth.refreshSession()`, OR
- The user signs out and back in.

**Downstream impact:** `proxy.ts`'s `/app/*` gate reads the account row via the RLS-claims-driven request client. With `tenant_id: null` on the JWT, the RLS predicate on `accounts` (which keys on the `tenant_id` claim) returns no rows, so the gate redirects back to `/onboarding`. The user is in a loop until the JWT expires.

**Fix paths** (codex suggests either):

**A. Force token refresh post-insert in `auth/callback/route.ts`:**
```ts
// After the upsert, before redirect:
await supabase.auth.refreshSession();
// — or, more surgical:
const { data: { session } } = await supabase.auth.getSession();
if (session?.refresh_token) {
  await supabase.auth.refreshSession({ refresh_token: session.refresh_token });
}
```
The refreshed JWT re-runs `custom_access_token_hook`, picks up the now-existing account row, and stamps a fresh `tenant_id` claim. Cleanest path.

**B. Decouple `proxy.ts`'s gate from the claim, fall back to `auth.uid()` lookup:**
In `proxy.ts`'s account-resolution function, if the claim is missing, look up the account by `owner_user_id = user.id` (which IS valid on the JWT). This avoids the cycle but adds a per-request DB read for any session whose claim is stale (also covers an edge case: an account that was deleted+recreated mid-session).

Codex's adjudication implies A is the surgical fix and B is the resilience-layer fix. Both are compatible — A repairs the data-plane invariant, B hardens the proxy against the same shape of bug recurring.

**Why the original review missed this:** the original review (2026-05-14, `de40c73`) ran BEFORE PR-1 added the atomic account insert in `auth/callback/route.ts`. At de40c73 the callback's read-then-insert was racy (the Orig P1 #3 finding), and the orig finding focused on the race, not the token-staleness consequence. Codex's adjudication now reads the post-PR-1 code where the race is gone — but the token-staleness defect of running the insert AFTER `exchangeCodeForSession()` is a different problem that PR-1's fix doesn't address.
